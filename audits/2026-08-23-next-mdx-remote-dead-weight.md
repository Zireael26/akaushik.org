## Summary

`next-mdx-remote@6.0.0` is dead weight. No runtime code imports it. The two MDX renderers that used to (`components/work/CaseStudyPage.tsx` and `app/writing/[slug]/page.tsx` via `MDXRemote`) now render pre-compiled modules from `lib/mdx/generated` via `getMdxModule`. A committed comment in `docs/CHANGELOG.md:128` already states this: “runtime code remains free of `next-mdx-remote`, though its type/test references still prevent dependency removal.”

Only two code edges keep the package installed:

1. **Type-only edge** — `lib/mdx-options.ts:4-7` types `MDX_OPTIONS` against `next-mdx-remote/rsc` (`type MDXRemoteOptions = NonNullable<ComponentProps<typeof MDXRemote>['options']>`). The value itself is just an object of `remarkPlugins` / `rehypePlugins` — the type is the coupling.
2. **Test-only edge** — `lib/mdx-options.test.ts:2-3,33-36` imports `serialize` from `next-mdx-remote/serialize` and `MDX_OPTIONS` to compile a fixture and assert highlighting markers. It is the only file that calls `next-mdx-remote` at test time.

Removing the dependency is therefore a **type + test migration plus manifest/lock cleanup**, not a runtime rewrite. The live plugin stack already lives verbatim in `scripts/build-mdx-modules.ts:48-55` against `@mdx-js/mdx` (the same compiler `next-mdx-remote` wraps). The risk is not “does the site still render” but “do we lose the dual-theme Shiki contract and introduce plugin drift between two copies of the same list.”

No size-saving claim is made here — no bundle/install measurement was run per the assignment.

## Removing the `lib/mdx-options.ts` coupling

### Current coupling

`lib/mdx-options.ts` (27 LOC):

```ts
import rehypePrettyCode from 'rehype-pretty-code';
import rehypeSlug from 'rehype-slug';
import remarkGfm from 'remark-gfm';
import type { ComponentProps } from 'react';
import type { MDXRemote } from 'next-mdx-remote/rsc';
type MDXRemoteOptions = NonNullable<ComponentProps<typeof MDXRemote>['options']>;
export const MDX_OPTIONS: MDXRemoteOptions = {
  mdxOptions: {
    remarkPlugins: [remarkGfm],
    rehypePlugins: [
      rehypeSlug,
      [rehypePrettyCode, { theme: { light: 'github-light', dark: 'github-dark-dimmed' }, keepBackground: false }],
    ] as never,
  },
};
```

* Value imports (`remark-gfm`, `rehype-slug`, `rehype-pretty-code`, `shiki` transitively) are **not** the coupling — those packages remain whatever the compiler is.
* The coupling is the **type** `MDXRemoteOptions` derived from `next-mdx-remote/rsc` and the export shape `{ mdxOptions: { remarkPlugins, rehypePlugins } }` which exists only to satisfy `MDXRemote`’s prop.

`scripts/build-mdx-modules.ts:48-55` keeps its own literals precisely to avoid importing that shape:

```ts
const REMARK_PLUGINS = [remarkGfm];
const REHYPE_PLUGINS = [
  rehypeSlug,
  [rehypePrettyCode, { theme: { light: 'github-light', dark: 'github-dark-dimmed' }, keepBackground: false }],
];
```

ADR-0019:33 notes the divergence risk explicitly: “Changing one without the other is a divergence.” Today that is two copies of the same list with the same values but different option wrappers.

### How to remove it (without breaking the plugin stack)

There are two clean end states. Either is fine; the audit recommends **(A)** because the stack already lives in the script.

#### (A) Delete `lib/mdx-options.ts` — script is canonical (recommended)

1. Make `scripts/build-mdx-modules.ts` the single source. Its `REMARK_PLUGINS`/`REHYPE_PLUGINS` are already the shipped stack (verified by `compile(..., { remarkPlugins: REMARK_PLUGINS, rehypePlugins: REHYPE_PLUGINS as any })` at `82-84`). Add the doc-line that used to live in `lib/mdx-options.ts` as a block comment above those constants (and cite ADR-0019), so future editors know where to change plugins.
2. Remove the cross-reference comments in that script that say “the plugin stack in `lib/mdx-options.ts`” (`25-27`) — reword to “the plugin stack below (ADR-0019)” — and remove HANDOFF.md:32-33’s “`lib/mdx-options.ts` no longer renders anything” line in the same PR or a doc follow-up.
3. The file deletion itself is `rm lib/mdx-options.ts`. No other source file imports `MDX_OPTIONS` (verified: only `lib/mdx-options.test.ts:3` does), so no runtime import breaks.

*If an intermediate “neutral” module is desired to keep a `lib/` entry point for tooling,* the same constants can be re-exported from `lib/mdx/plugins.ts` typed against `unified`/`@mdx-js/mdx`, not `next-mdx-remote`:

```ts
// lib/mdx/plugins.ts — no next-mdx-remote anywhere
import rehypePrettyCode from 'rehype-pretty-code';
import rehypeSlug from 'rehype-slug';
import remarkGfm from 'remark-gfm';
export const REMARK_PLUGINS = [remarkGfm] as const;
export const REHYPE_PLUGINS = [
  rehypeSlug,
  [rehypePrettyCode, { theme: { light: 'github-light', dark: 'github-dark-dimmed' }, keepBackground: false }],
] as const;
```

The script then `import { REMARK_PLUGINS, REHYPE_PLUGINS } from '../lib/mdx/plugins'`. Type it as `PluggableList` from `unified` if strictness is wanted, not as `MDXRemoteOptions`. This keeps a `lib/` owner without reintroducing the dead dep. Either pure-delete or this neutral extract satisfies the brief; do not keep the `MDXRemote`-typed wrapper.

#### (B) Keep `lib/mdx-options.ts` but strip its dep (alternative)

Keep the file, delete lines `4-7` (`ComponentProps`, `MDXRemote`, `MDXRemoteOptions`), and change the export to the neutral `REMARK_PLUGINS`/`REHYPE_PLUGINS` (or a plain `REMARK_PLUGINS`/`REHYPE_PLUGINS` object without `mdxOptions` nesting). The script imports from it. Viable but retains a file the runtime never reads; (A) is simpler unless a `lib/` owner is explicitly wanted.

In either case, `remark-gfm`, `rehype-slug`, `rehype-pretty-code`, and `shiki@^4.3.0` **stay** in `package.json` — they are the highlighting stack. Only `next-mdx-remote` leaves.

## Replacing or deleting `lib/mdx-options.test.ts`

### What it currently proves

`lib/mdx-options.test.ts` is a PR #92 proxy for the `shiki` 1→4 major bump. It:

* calls `serialize(source, { mdxOptions: MDX_OPTIONS.mdxOptions })` — the same codepath `MDXRemote` uses;
* asserts three observable markers on the `compiledSource` string:
  * `data-rehype-pretty-code-figure` — `rehype-pretty-code` ran;
  * `--shiki-light` and `--shiki-dark` in the quoted style-object keys — Shiki emitted per-token CSS vars for **both** themes (dual-theme contract);
  * `github-light github-dark-dimmed` — the configured theme pair is active;
* plus a guard: a fence with no language tag must **not** emit `--shiki-light` (the single plain block on `/writing/trellis` precedent — without this, a silent single-theme regression could still pass the first two assertions).

It compacts three risks into one fast unit test: “our exact plugin list still tokenises language-tagged fences in dual-theme mode and leaves plain fences alone.” Losing that without a replacement is the biggest regression risk of the removal.

### How to keep coverage without `next-mdx-remote`

`@mdx-js/mdx@3.1.1` is already a `devDependency` (added in D8) and is what `next-mdx-remote` wraps transitively (`pnpm-lock.yaml` shows `next-mdx-remote` depends on `@mdx-js/mdx` + `@mdx-js/react`). The same assertions can be made against `@mdx-js/mdx`’s `compile`, which is what `scripts/build-mdx-modules.ts` actually uses.

**Minimal retarget (keeps the test fast and local):**

Replace the harness in `lib/mdx-options.test.ts:32-39`:

```ts
// before
import { serialize } from 'next-mdx-remote/serialize';
import { MDX_OPTIONS } from './mdx-options';
async function compiledSourceFor(source: string) {
  const result = await serialize(source, { mdxOptions: MDX_OPTIONS.mdxOptions });
  return result.compiledSource;
}
```

with:

```ts
// after — no next-mdx-remote
import { compile } from '@mdx-js/mdx';
import remarkGfm from 'remark-gfm';
import rehypeSlug from 'rehype-slug';
import rehypePrettyCode from 'rehype-pretty-code';

// either import REMARK_PLUGINS/REHYPE_PLUGINS from the new canonical (lib/mdx/plugins.ts)
// or keep them literal — but import, don’t duplicate, so drift is impossible
import { REMARK_PLUGINS, REHYPE_PLUGINS } from './mdx/plugins'; // or '../scripts/…' neutral export

async function compiledSourceFor(source: string): Promise<string> {
  const vfile = await compile(source, {
    remarkPlugins: REMARK_PLUGINS as any,
    rehypePlugins: REHYPE_PLUGINS as any,
    outputFormat: 'program',
  });
  return String(vfile);
}
```

Assertions stay verbatim:

```ts
expect(out).toContain('data-rehype-pretty-code-figure');
expect(out).toContain('--shiki-light');
expect(out).toContain('--shiki-dark');
expect(out).toContain('github-light github-dark-dimmed');
// and
expect(out).not.toContain('--shiki-light'); // plain fence
```

`String(vfile)` from `@mdx-js/mdx` contains the same highlighted HTML fragment (with Shiki’s `span` + CSS vars) embedded in the generated program, so the same substring checks hold. Verify once by diffing `compiledSource` from `serialize` vs `String(compile(...))` on the two fixtures — they differ in wrapper JSX but share the inner highlighted code payload.

**If `lib/mdx-options.ts` is deleted outright,** move this test to `lib/mdx/plugins.test.ts` (or `scripts/build-mdx-modules.test.ts`) so the spec lives next to the new owner. Either name is fine; do not leave the old path if the module it tests is gone.

**Alternatives considered and why not primary:**

* *Build-artifact assertion* — run `tsx scripts/build-mdx-modules.ts` on a temp fixture (one language-tagged fence + one plain fence), read `lib/mdx/generated/writing__<slug>.mdx.js`, assert the same markers. Valid and closest to shipped code, but slower and couples the unit test to filesystem/OUT_DIR churn. Useful as a second backstop behind the compile-string test, not a replacement.
* *Delete test and rely on e2e / manual eyeballing* — rejected. The current e2e suite has no dual-theme token assertion; a Shiki major that silently drops `--shiki-dark` would ship.
* *Keep `next-mdx-remote` as a devDependency for a test-only dep* — defeats the dead-weight removal; `@mdx-js/mdx` is already the devDep that provides the same compiler without the RSC wrapper.

Coverage: `vitest.config.ts:46` excludes `lib/mdx-options.ts`. After the file is gone, delete that line. If a new `lib/mdx/plugins.ts` is a trivial constant array, add it to the same exclude list (like `lib/about-copy.ts`) — the behavioral proxy is the test file, not the constants.

## What could break

### 1. Typecheck — `tsc --noEmit` and `tsc6 --noEmit`

* **If `next-mdx-remote` is removed before the type import is gone:** `lib/mdx-options.ts:5` `from 'next-mdx-remote/rsc'` fails with `TS2307: Cannot find module 'next-mdx-remote/rsc'` and `MDXRemoteOptions` becomes unresolvable. This blocks `typecheck:compare` and `cf:build`’s type gate.
* **If `MDX_OPTIONS` shape changes but the test still consumes `.mdxOptions`:** `lib/mdx-options.test.ts:36` `MDX_OPTIONS.mdxOptions` no longer exists once the file is retargeted to `REMARK_PLUGINS`/`REHYPE_PLUGINS`. Silent drift if the test is not retargeted atomically.
* **If a hidden import remains:** grep found none, but a Husky hook or generated `next-env.d.ts` change could resurface — `tsc` will surface it. Safe to verify with `grep -r MDXRemote --include='*.ts' --include='*.tsx'`.

*Mitigation:* atomically (a) retarget or delete `lib/mdx-options.test.ts` and (b) delete or neutralise `lib/mdx-options.ts` in the **same PR** as the `package.json` edit, or do the file deletion first and only then delete the dependency in a second commit of the same PR. Never push a commit that deletes the dep while `lib/mdx-options.ts` still exists.

### 2. Plugin drift — Shiki dual-theme + GFM contract

* The shipped article and work bodies hide behind `rehype-pretty-code`’s dual-theme tokenisation. If the literal in `scripts/build-mdx-modules.ts:52-54` drifts from what any remaining `lib/` copy asserts, code fences ship with wrong tokens (single theme, wrong names, `keepBackground: true` leaking backgrounds, or plain `<pre>` with no tokenisation).
* The CSS comments in `work-detail.css`/`writing-detail.css` and the primer assume the same plugins. Not a build break, but author-visible drift.
* `remark-gfm` is equally load-bearing — tables and task lists in MDX without it would render as raw markdown. No current test asserts GFM explicitly but the corpus uses tables/lists; a removal that drops the plugin would be visible only by eyeballing.

*Mitigation:* make the new test import the **same** `REMARK_PLUGINS`/`REHYPE_PLUGINS` the script uses (so a divergence is a compile error or a single-edit change), and keep the three Shiki assertions plus the plain-fence guard. Optionally add a GFM probe: `compile('| a | b |\n|---|---|\n| 1 | 2 |', { remarkPlugins: REMARK_PLUGINS, … })` → contains `<table`.

### 3. Shiki dual-theme / code-fence contract

* **Dual-theme:** `theme: { light: 'github-light', dark: 'github-dark-dimmed' }, keepBackground: false` is the contract the CSS and `prefers-color-scheme` depend on. Changing it to a single string theme would still highlight but break dark-mode token swapping (no `--shiki-dark`).
* **Plain fence:** the only plain (no language) code block on the shipped site lives at `/writing/trellis` (per the test comment on `:64-66`). The guard `expect(out).not.toContain('--shiki-light')` for ```` ``` ```` (no tag) ensures that un-tagged fences stay plain — if a future `rehype-pretty-code` version starts tokenising plain fences, the dual-theme assertions would give false positives.
* **`rehype-pretty-code` ↔ `shiki` peer drift:** `rehype-pretty-code@0.14.3` peerDepends on `shiki@^1 || ^2 || ^3 || ^4` (`pnpm-lock.yaml:3855`). A future `shiki@5` that no longer supports `{ light, dark }` object themes would break at runtime. The proxy test catches that at unit-test time.

*Mitigation:* keep the test’s four expectations exactly; do not narrow them.

### 4. Generated MDX modules — `lib/mdx/generated`

* `scripts/build-mdx-modules.ts` writes `lib/mdx/generated/index.ts` (registry of `MDX_MODULES` + `getMdxModule`) and `modules.d.ts` (ambient `declare module '*.mdx.js'`) plus one `*.mdx.js` per body (19 files today). These are git-ignored and regenerated by `prebuild`/`pretypecheck`/`pretest`.
* **If the script is changed to import from a `lib/` module that itself imports the script (cycle),** `prebuild` will fail.
* **If `getMdxModule` signature changes** (e.g. renamed, or registry keys change from `${type}/${slug}`), `CaseStudyPage.tsx:75` and `app/writing/[slug]/page.tsx:282` break — both call `getMdxModule('case-studies'|'writing', slug)`.
* **If `compile` options change** (`outputFormat`, `development`, `jsx`) the generated `*.mdx.js` may emit a different shape that `createElement(mdx)` no longer renders.

*Mitigation:* after any plugin or compile-option edit, run the script once and inspect one generated file for `data-rehype-pretty-code-figure` and `--shiki-light`/`--shiki-dark`, and confirm `CaseStudyPage`/`WritingPost`’s `MdxBody` still `createElement`s the module.

### 5. `pretypecheck` / `pretest` hooks

`package.json:41-42`:

```json
"pretypecheck": "tsx scripts/build-content-bundle.ts && tsx scripts/build-mdx-modules.ts",
"pretest":     "tsx scripts/build-content-bundle.ts && tsx scripts/build-mdx-modules.ts"
```

* These mean **every** `pnpm typecheck` and `pnpm test` first regenerates `lib/mdx/generated` and `lib/content-bundle.generated.ts`. If `scripts/build-mdx-modules.ts` starts importing from a file that is not committed yet (e.g. `lib/mdx/plugins.ts` not yet added), both hooks fail and look like a typecheck/test failure.
* If `next-mdx-remote` is removed and the old `lib/mdx-options.test.ts` is not retargeted, `pretest` succeeds (it regenerates modules) but `vitest run lib/mdx-options.test.ts` fails at import of `next-mdx-remote/serialize`.
* Deleting the package without running `pnpm install` leaves it in `node_modules` — tests may still pass locally but fail in CI where the lockfile is authoritative.

*Mitigation:* commit `lib/mdx/plugins.ts` (if added) before deleting `lib/mdx-options.ts`; always regenerate the lockfile with `pnpm install` in the same PR; verify `pnpm typecheck`/`pnpm test` in a clean checkout (`rm -rf node_modules && pnpm install --frozen-lockfile`).
